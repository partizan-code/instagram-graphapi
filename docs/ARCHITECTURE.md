# Архитектура

Плоская структура, без CLI, классов клиента, моделей и БД.

| Файл | Назначение |
| --- | --- |
| `main.py` | Чтение аккаунта и последней страницы Direct через Meta Unified Login |
| `config.py` | Загрузка .env, параметры API и размеры страниц |
| `api.py` | Общие GET/POST к graph.facebook.com, Bearer, тайм-аут, безопасные ошибки |
| `logging_config.py` | Общий Loguru logger, только консоль |
| `auth.py` | Unified Login: вход с config_id/state, обмен кода, сохранение и явный выпуск нового токена |
| `publisher.py` | Отдельные функции публикации фото/Reels/Stories/каруселей |
| `webhook_server.py` | Отдельный FastAPI/Uvicorn-приёмник с проверкой подписи Meta |
| `tests/` | Изолированные проверки с HTTP-моками и заблокированной сетью |

Чтение: META_ACCESS_TOKEN → graph.facebook.com → assigned_instagram_accounts →
Instagram account ID → conversations со вложенными messages.
Обычный запуск не вызывает авторизацию, продление токена или публикацию.
Авторизация открывает facebook.com, HTTP-операции используют graph.facebook.com.
Публикации адресуются Instagram account ID; `/me` обозначает системного пользователя.

## Общий HTTP-слой

`api.request(session, path, *, method="GET", **params)` выполняет запрос в
переданной Requests-сессии. `api.call(path, token="", *, method="GET", **params)`
создаёт и закрывает собственную сессию, при наличии токена добавляя Bearer-заголовок.
`main.py` использует одну сессию для чтения аккаунта и диалогов; `auth.py` и
`publisher.py` вызывают `call()`.

Адрес собирается из `GRAPH_BASE`, `META_API_VERSION` и относительного пути.
GET передаёт параметры в query, POST — в form data. Редиректы запрещены;
тайм-аут Requests 30 секунд действует отдельно на подключение и чтение ответа,
а не на всю операцию. Ответы закрываются контекстным менеджером.
Автоматических повторов и обхода пагинации нет.

Слой проверяет JSON-объект, HTTP-статус и поле `error`. Вместо сырой ошибки Meta
возвращается `RuntimeError` с HTTP-статусом и числовыми code/subcode; сетевые ошибки
заменяются общим сообщением. Токен, тело ответа и исходное HTTP-исключение в эти
сообщения не включаются. Обмен OAuth-кода передаёт реквизиты Meta в запросе,
поэтому сырые запросы и URL также нельзя добавлять в журнал.

## Логирование и данные

`configure_logging()` настраивает один консольный sink уровня INFO в stderr,
без файлов, backtrace и диагностики локальных переменных. Повторная настройка
не дублирует записи. Секреты и URL пагинации в logger не передаются.
Сценарий Direct намеренно выводит ID и сообщения; управляющие символы терминала
экранируются. Webhook-сервер выводит только результат обработки и счётчики,
без ID и содержимого событий. БД и постоянного хранения переписки нет.

## Входящие webhooks

Webhooks: tuna HTTPS → `127.0.0.1:8000/webhook` → проверка challenge либо
HMAC-SHA256 → счётчики событий в общем Loguru logger. Сервер запускается задачей
`webhook` без аргументов и запрашивает адрес туннеля через `input()`; задача
`tunnel` запускает tuna с отключённой инспекцией. HTTP-журналы Uvicorn отключены
через общую конфигурацию логирования. Отправки и хранения переписки нет.
